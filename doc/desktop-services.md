# Plugins and desktop services

The `NeoAstra.Desktop` namespaces are the statically composed desktop-service layer included in `NeoAstra.dll`. The implementation is AOT-compatible and does not scan assemblies, load adapters dynamically, or use runtime reflection.

## Security model

Adding a plugin, service object, permission catalog, or renderer command declaration grants no authority. `AddNeoAstraDesktopPermissions` only adds declarations to capability tooling. Applications must separately register RPC handlers and grant the exact permissions/scopes needed by each trusted view. The official declarations use `desktop.*` command names and sensitive/high risk for clipboard reads, opener operations, native UI mutation, shortcuts, outbound drag, and safe storage. File, URL, clipboard, dialog, and notification operations requiring argument policy declare their scope family.

Service inputs and retained resources are bounded. File paths are canonicalized beneath explicit roots, URL origins are exact scheme/IDN-host/effective-port allowlists, or the one scope `NeoUrlScope.AnyWebAddress` for an application whose content links anywhere (any absolute HTTP(S) address with a host and without credentials, control or white-space characters, of at most 4096 characters; no `mailto:` and no other scheme), opener APIs expose fixed intents rather than arbitrary executables or verbs, command arguments use `ProcessStartInfo.ArgumentList`, and helper processes have deadlines, bounded output, and process-tree termination. Clipboard and secret bytes are copied; safe-storage enumeration is intentionally absent. Drag file paths become document-session-scoped opaque tokens. Trusted C# outbound calls consume explicit short-lived one-shot tokens; renderer outbound calls expose no token and instead consume a current native pointer gesture bound by the host to the source view and active document session.

Canonical path checks prevent lexical traversal and resolve existing links before authorization, but a pathname handed to an external OS application cannot be held open atomically across handler launch. Applications must therefore use roots that an untrusted renderer cannot rename or replace; this is an OS pathname TOCTOU boundary, not a substitute for handle-based file I/O. Creatable save paths authorize the resolved parent and leaf separately and must be revalidated by any later privileged consumer.

Desktop APIs are backend APIs by default. Registering `AddNeoAstraDesktopHandlers` exposes the reviewed renderer subset, but grants nothing until the view receives each explicit capability. Menus and tray descriptors route stable command IDs to backend handlers rather than evaluating JavaScript strings.

## Composition and lifecycle

Register plugins with explicit factories:

```csharp
var plugins = new NeoPluginBuilder()
    .AddNeoAstraDesktop(services)
    .Build();
```

Plugin IDs and dependencies are validated and topologically sorted with ordinal tie-breaking. The host configures plugins, creates one explicit adapter per plugin, attaches adapters on the UI dispatcher, and transitions to ready in deterministic order. Stop revokes plugin work first, disposes tracked view/window/session resources in reverse ownership order, detaches adapters, and disposes plugin service graphs. Startup failure rolls back already-created resources. Disposal is idempotent and aggregates teardown failures.

`NeoPluginOwner` identifies application, window, view, session, or resource ownership. Track native registrations through `NeoPluginContext.TrackAsync` so shortcuts, tray items, callbacks, and broker tokens cannot outlive their owner.

On macOS and Windows, tray activation handlers run before native menu presentation. If a handler removes or replaces that item (including removal followed by recreation of the same ID), or disposes the tray service, that activation does not open a menu. Otherwise the existing platform popup policy is unchanged: macOS opens the menu for primary or secondary activation; Windows opens it for secondary activation. Resources used by a popup stay alive until its native tracking loop returns, even if nested dispatcher work removes/replaces the item or disposes the service. On macOS the status item and its callback target also stay alive until the activation handler returns, because AppKit is still dispatching the click from them. Retired menu command-ID callbacks are ignored.

Windows context-menu tracking likewise keeps retired native menus alive until the outermost tracking loop returns. Removal, replacement, service disposal, or owner closure during tracking prevents the retired menu's returned selection from dispatching. The owner HWND remains application-owned: the menu presenter neither keeps a closed window alive nor destroys it.

## Platform support

Support is reported per service through `NeoCapabilityInfo`; callers must not infer support from OS name. `None` and `Limited` are expected outcomes and never cause an insecure plaintext or unrestricted fallback.

`NeoExternalOpener.OpenUrlAsync` opens a URL that the `NeoUrlScope` of the service accepts and reports `Denied` for any other, before anything is launched. A scope is a list of exact origins, or `NeoUrlScope.AnyWebAddress` when the content of the application links anywhere, as a chat or a document viewer does:

```csharp
var desktop = NeoDesktopServices.CreateSystem(
    "com.example.app", "Example", "1.0", privateDataDirectory,
    NeoUrlScope.AnyWebAddress, openFileRoots, revealFileRoots, openFileIntents);
var status = await desktop.Opener.OpenUrlAsync(new Uri("https://example.org/page"));
```

`AnyWebAddress` checks the form of an address and not where it leads: the application still decides which links it offers, and should show the user the address that a link opens.

Windows executables that use the dialog service must activate Common Controls v6 in their application manifest because `TaskDialogIndirect` is a v6 API. The advanced sample's `app.manifest` provides this dependency for both normal and NativeAOT builds.

Native inbound drops are routed only to the active trusted renderer document session for the target view. On Windows, NeoAstra disables WebView2's browser-native external drop and replaces the OLE targets on the controller window and every descendant renderer window, including descendants owned by the WebView process. Native code accepts bounded `CF_HDROP`, Unicode text, and URL data; file paths are canonicalized and passed directly to the existing file-scope broker, so paths never enter page JavaScript, which receives only opaque tokens.

HTML5 drag and drop inside the page keeps working: a drag that started in the page (an element with `draggable`, selected text, a link) and a drag that carries none of the file, text, or URL formats NeoAstra takes (for example only a custom MIME type such as `application/x-my-app-item`) belong to the page, which receives `dragenter`, `dragover`, and `drop` with its own data, and they never reach the host as inbound drops. On Windows, WebView2's own OLE drop target lives in its browser process, cannot be called by NeoAstra's replacement, and is withdrawn while external drops are disabled, which disables in-page drops too. NeoAstra therefore asks WebView2 (DevTools `Input.setInterceptDrags`) to report the drags that start in the page instead of running its own drag loop, and runs them itself: an OLE drag loop of the application carries their text, URL, and custom MIME data (so a drag can still leave the window, as text, a URL, or Chromium custom data), and NeoAstra's drop target gives the page `dragenter`, `dragover`, and `drop` through `Input.dispatchDragEvent`, then the drag ends in the page with `dragend`. An external drag with only formats NeoAstra does not take reaches the page the same way. The cursor shows the first effect the source allows (copy, then move, then link), whether or not the element under it accepts the drop, and a page drag shows no drag image. Drags started by the application itself (`dragDrop.outbound`) stay inbound drops.

On Windows, a page drag dropped on another view of the application, such as a tab dragged to another window, belongs to the page of that view too: it receives `dragenter`, `dragover`, and `drop` with the data the drag started with (its text, URL, HTML, and custom MIME types), and its host gets no inbound drop. NeoAstra recognizes such a drag by a nonce of the drag that runs, which another process cannot supply, so an external drag that only claims to be a page drag stays an external drop. The source page then ends its drag with a `dragend` whose `dropEffect` is `none`, as for a drag released elsewhere: WebView2's DevTools protocol ends a drag of a page only with a drop on that same page or with a cancel, and does not tell NeoAstra whether the receiving page accepted the drop. The receiving page gets its `drop` before the source page gets `dragend`: NeoAstra waits, for at most two seconds, for the drop to reach the receiving page before it ends the drag in its source. Other applications still get the text, URL, and custom data of a page drag, without its HTML.

The host of the source view learns how the drag ended from `NeoAstra.PageDragEnded`, raised once for each drag of its page that NeoAstra runs, after the drop reached the receiving page. `NeoPageDragEndedEventArgs` tells what the `dragend` of the page cannot:

| Member | Value |
| --- | --- |
| `Outcome` | `Canceled` (the Escape key), `NotDropped` (released over the desktop, outside every window, or over a target that refused it), `DroppedOnView`, or `DroppedOnOtherApplication` |
| `TargetView` | The view of the application that the drag was released over, the source view included, for `DroppedOnView` |
| `Effect` | What the drop target answered: `Copy`, `Move`, `Link`, or `None`. For a drop on a view of the application, the first effect that the page allowed (copy, then move, then link) |
| `ScreenPosition` | The pointer when the drag ended, in the units of `NeoWindow.Position` |
| `Items` | The data of the drag, each a MIME type and its data, as the page set them |

An application with tabs that move between windows takes these together. `DroppedOnView` with another view tells the host which window the tab went to; whether that page accepted it, its `drop` handler says, since an engine does not report it. `NotDropped` with a `ScreenPosition` outside every window of the application is a tab torn out, for which the host opens a window there. `Canceled` leaves the tab where it is.

```csharp
view.PageDragEnded += (_, drag) =>
{
    var tab = drag.Items.FirstOrDefault(item => item.MimeType == "application/x-my-app-tab")?.Data;
    if (tab is null) return;
    if (drag.Outcome == NeoPageDragOutcome.NotDropped && !IsOverAWindow(drag.ScreenPosition))
        OpenWindowWithTab(tab, drag.ScreenPosition);
};
```

On macOS a drag whose source is a web view of the application gets only WebKit's handling, between views of different windows as well, and on Linux NeoAstra's GTK drop target refuses every drag that started in the application, so WebKitGTK's own target takes it, including a `dragDrop.outbound` drag dropped back on a view of the application. NeoAstra does not run those drags and raises no `PageDragEnded` there. WebKit gives the source page what its drop target answered instead: on macOS the `dropEffect` of `dragend` is the operation of the drop, and `none` for both a cancel and a release where nothing took the drag; WebKitGTK 4 ends the drag in the page with the action of a finished drop, while its handler of a canceled drag does not end it in the page. This is what the code of WebKit does (`WebViewImpl::draggingSessionEnded` and `DragSource` of GTK 4); it has not been run on those platforms by a test.

View/window labels remain metadata, while navigation, transport-session rotation, renderer teardown, view disposal, and window closure revoke the old session's file tokens. A renderer calls `dragDrop.outbound(viewLabel, items)` from its native drag-start handler; background calls or calls after the source gesture expires, is reused, targets another view/session, or is invalidated by navigation return `Denied`.
| Window state/polish | Source-generated atomic persistence, topology/scale clamping, native icon/attention/taskbar progress/DWM title intent/capture affinity | Persistence plus app icon, attention, dock badge, represented document and sharing restriction; per-window icon/progress/title-only theme semantics are unavailable or limited | Persistence plus GTK4 window sensitivity; GTK4 removed per-window file icons and urgency hints, and generic progress/badge/title theme/capture exclusion has no reliable portable GTK/Wayland semantic |

Headless Linux commonly reports clipboard, notification, tray-host, shortcut, and credential services unavailable. Wayland/X11 and session D-Bus availability are detected explicitly. Linux tray creation reports unsupported when the desktop does not currently implement the StatusNotifier watcher protocol, preventing close-to-tray applications from hiding their only recovery window. Existing items are re-registered if the watcher restarts. macOS and Linux runtime conformance remains a CI responsibility; do not convert an unavailable runtime into a passing emulation.

`NeoMenuItem.RoleItem(id, role)` requests a framework-localized standard label. GTK4 removed the stock menu-item labels used by the former backend, while Win32 and AppKit expose native role commands/selectors but no reliable complete localized label set. These presenters reject the implicit form instead of displaying hard-coded English. Use `NeoMenuItem.RoleItem(id, role, localizedText)` with application-localized Unicode text on every platform for portable presentation. The label changes presentation only: activation remains a fixed native role command/selector and never evaluates arbitrary JavaScript. Linux edit roles select a live WebKit view by actual `OwnedWindow` identity; the ordinally smallest non-null view label wins, with native-handle ordering only for unlabeled ties. Missing, zero, replaced, or disposed handles disable the item or make activation a no-op before any GTK/WebKit call.

## Persistence and secrets

`NeoJsonWindowStateStore` accepts application-chosen bounded keys and writes one source-generated JSON record atomically. Restore validates finite scale values, rejects malformed display snapshots, chooses the saved or best-intersecting display, keeps the size that the content of the window had, clamps to the work area of that display, and normalizes minimized state unless explicitly requested. A window that is over several displays stays over them, with the identifier and the scale of the display it is mostly on: it is clamped to the rectangle around the work areas of the displays it is on, which leaves a window that is within that rectangle where it was. Where the displays are not aligned that rectangle has parts that no display shows, so the window stays over them only while a stretch of its title bar is on the work area of one display: of its top 32 logical units, half the width of the window or 100 logical units, whichever is less. With less than that, and when a display it was on is gone, it comes back whole on the display it is mostly on. What is compared with the displays, shrunk, and moved is the rectangle that the window shows, `NeoWindowPlacement.NormalFrame`, which the controller saves from `NeoWindow.FrameBounds` with the normal bounds: on Windows a window whose visible edge was at the edge of a display has a position beside that edge and stays there, and the title bar of a window that is shrunk to a work area is counted in. The returned placement has the normal bounds to assign and the frame the window then shows. A placement without a frame, as one saved by an earlier version, is compared by its normal bounds. A file with a frame has a member that NeoAstra 1.2 and earlier refuse: an application that goes back to such a version finds no placement once and places its window as a new one. A placement pairs the window position with its client size, the values `NeoWindow.Position` and `NeoWindow.ClientSize` both report and accept, so restoring it reproduces the window whatever its frame or title-bar style. It is in the units of the window, with the `ScaleFactor` that the window had. On macOS and with GTK, where a window is counted in logical units, the window comes back with the saved size on every display. On Windows, where an application that is aware of display scaling counts a window in the pixels of its display, the size follows the scale of the display that the window comes back on, and the display snapshots, which are in logical units, are compared with the window in those pixels. `NeoWindowStateController` saves the placement that its window goes back to. The normal bounds are the bounds of the window while it is in its normal state, so a window that is maximized, fullscreen, or minimized keeps the ones it had before, and the state is the state of the window, or the one it had before it was minimized. The controller reads the window once it has been left alone for its delay. A write that the store refuses is reported to the log of the application as an error of the category `window.state`.

`NeoSafeStorage.CreateSystem` accepts a stable application namespace and an absolute private data directory. Windows persists only DPAPI-protected bytes and zeroes temporary protected/native buffers. macOS uses binary-safe Security.framework calls and zeroes Keychain-owned retrieved bytes before freeing them. Linux passes base64 secret bytes over redirected standard input to Secret Service and zeroes encoded/captured buffers. Retrieval returns an owned byte array; applications should zero it with `CryptographicOperations.ZeroMemory` as soon as possible.

## Testing

`TrayActivationTests` exercises the production macOS and Windows presenter sources with a recording native boundary, without an interactive desktop. It covers handler-triggered removal, replacement, same-ID recreation, service disposal, and mutations inside popup tracking, including resource release and rejection of stale commands. These deterministic lifetime regressions supplement rather than replace native desktop-session conformance.

`ContextMenuActivationTests` uses the same recording boundary for Windows context-menu tracking, including owner closure, nested popups, exception cleanup, and unchanged live-menu selection. Native HWND discovery is stubbed separately; real window/view binding remains covered by the desktop-session fixtures.

`WindowsMenuTests` exercises repeated window-menu show/hide requests through browser RPC with an active WebView2, checks the actual Win32 menu attachment, and closes the window while the menu is still visible. This is fresh-session baseline coverage, not coverage of every preceding interaction in the advanced sample.

Use `NeoFakeDialogs`, `NeoFakeClipboard`, recording presenter adapters, and the test-emulated shortcut mode for deterministic tests. Focused tests cover static metadata/handler/permission/schema consistency, grant-free backend registration, command/disposal races, immutable menu/tray presenter replacement and callbacks, descriptor limits and accelerators, notification rollback, clipboard ownership, scope denial before opener launch, owner-scoped one-shot drag tokens, corrupt/off-screen window state, per-feature polish semantics, Windows DPAPI persistence, and bounded child-process output. The Windows desktop-session fixture verifies that the controller and every recursively enumerated renderer child have replacement OLE targets, then verifies delivery routing and token release on navigation; the cross-platform fixture also creates real native menus, context ownership, tray/status items, modal owner trees, state transitions, and cross-thread service updates (Linux under Xvfb). Interactive pointer drag completion remains a manual desktop-session check because unattended simulation can target unrelated user windows; runtime evidence otherwise depends on those target runners and available desktop services.

Window file APIs are backend-trusted APIs. Renderer `desktop.window.set-icon` and `desktop.window.set-represented-file` additionally require `window:files` with a filesystem scope; all other window polish operations require `window:polish` and a live owner window.

`WindowPolish.SetIconAsync(window, path)` takes the full path of an existing .ico file on Windows (a .png file is `Unsupported` there). The window gets two icons from the file: a big one, which the taskbar and Alt+Tab show, at the `SM_CXICON` size of the scale of the window's display (32 pixels at 100%, 64 at 200%), and a small one, which the title bar shows, at the `SM_CXSMICON` size (16 and 32 pixels). Each is the picture of the file that suits its size best, so an .ico file should hold the sizes of the scales its users have (16 to 64 pixels, and 256 for the largest views). When the window moves to a display of another scale, both are loaded again from the file at the sizes of that scale; a file that can no longer be loaded leaves the icons of the previous scale. The service destroys the icons when the window closes or when the service is disposed, and holds icons for at most 128 windows at a time.

Without a call, a window on Windows shows the icon of its executable, when the executable has one: the first icon group of its resources, the one Explorer shows, which for a .NET application is its `<ApplicationIcon>`. The window takes it at the same two sizes and takes it again when it moves to a display of another scale, so an application whose executable has its icon needs neither an .ico file beside it nor a call. An icon that the application gives the window (with `SetIconAsync` or a `WM_SETICON` of its own) takes its place, and when the application takes its icon away the window shows the icon of the executable again. An application started through `dotnet app.dll` runs in `dotnet.exe`, whose icon is the one of .NET. On macOS the file becomes the application icon of the Dock; Linux reports `Unsupported`.

Capture protection is defense in depth only: it cannot stop cameras, privileged software, or every capture implementation.

Renderers granted `window:polish` can call `window.extraSupport()` before presenting platform-specific window controls. It returns the current support level and explanatory details for attention, progress, badges, represented-document state, content protection, and title-bar themes. Applications should enable `Native`, `Emulated`, and `Limited` features, account for the documented limitations, and omit or disable `None` features rather than requiring users to discover support through a failed action.

The frontend client exposes current-window state and the asynchronous management operations that are safe to invoke over RPC: title, position/size constraints, visibility/focus, presentation state, decorations, title-bar style, resize policy, always-on-top, taskbar membership, and close. They require `window:management` or the separate high-risk `window:close` capability. `window.onStateChanged` reports snapshots after native state, focus, and title-bar changes, and `window.attachTitleBar` publishes the title-bar layout to CSS; see [chromeless windows](chromeless-windows.md). `window.onCloseRequested` installs one document-session-owned interceptor, awaits all registered frontend handlers within the native close deadline, and fails closed if the renderer disconnects or does not answer. Calling `preventDefault()` can therefore hide the current window without destroying its WebView. Native-handle access remains backend-only. `window.startDrag` and `window.startResize` begin a native move or resize only while the primary button of the originating press is still held, so a request that arrives after the release reports `Canceled` instead of moving the window. `application.requestQuit` requires `application:quit`, enters normal bounded quit negotiation, and never maps to forced shutdown.

On Windows the keyboard follows the page of a window: when the window itself gets the keyboard focus (on activation, after a switch to another application and back) or a view is created in a window that holds it, NeoAstra moves it into the browser of the first visible view, which gives it back to the element of the page that had it. Before, nothing could be typed in the page until it was clicked.
